## Project direction

Read [the team project brief](docs/project-brief.md) before planning or changing product behavior. It defines Vehicle Health Agent and the implementation priorities.

- Build an agent driven by continuous vehicle ECU data, starting with overheating, with multi-signal reasoning and evidence/confidence.
- Prioritize levels 1–2: scenario-based telemetry simulation, explainable diagnosis, user consent before actions, and one complete action workflow.
- The intended demo simulates the data source; downstream rules, AI calls, response handling and persistence should be real. The brief explicitly allows fixed garage lists, seeded history and simulated next-day controls as later simplifications. Clearly label these boundaries.
- Current frontend still uses mock analysis and browser-local history; do not present these as completed real AI/backend integration. Backend is handled by another teammate.
- Keep the user's local-only 3D asset requirement. BMW M2 is currently the only shipped car model.
- Prefer one complete, reliable flow. Defer levels 3–4 before compromising levels 1–2.

### Backend architecture reference (2026-09-12)

Read [Vehicle Safety Agent architecture](docs/vehicle-safety-agent-architecture.md) when planning integration. This newer proposal prioritizes an overheating safety incident workflow over garage booking: monitor response, find a safe stop, obtain confirmation, request rescue, monitor stabilization. It uses one LLM agent; the Prediction & Rule Engine produces structured technical risk, severity, confidence and evidence. The LLM explains and orchestrates rather than diagnosing directly from raw telemetry.

Frontend should reflect backend incident state (`MONITORING`, `WARNING`, `WAITING_CONFIRMATION`, `ACTION_IN_PROGRESS`, `CRITICAL`, `STABILIZING`, `RESOLVED`) and vehicle motion state. Preserve per-vehicle/incident identity and pending confirmations across telemetry updates. Distinguish severity from workflow status. Navigation, rescue and sharing vehicle/location data need explicit confirmation; no direct vehicle control in MVP. Real garage booking is outside this proposed MVP.

This is architecture reference, not evidence that backend endpoints exist or these workflows are implemented. Current frontend still has local rule evaluation, synthetic telemetry and local demo garage appointments. Do not silently claim backend integration, actual rescue, confidence values or incident transitions. See [integration notes](docs/frontend-backend-integration.md).

### Quiet, talk, and demo pause (2026-10-16)

The presenter can silence alarms without changing the safety decision, then talk to Neuron for more than one turn. Details and the limits are in `../docs/alert-control-and-conversation.md` (local note, not in the public repo) and section 9 of `../docs/demo-runbook.md`.

- `lib/agent/audio-focus.ts` is the only playback policy. Quiet for 60 seconds cuts the horn (`AlertTone.stop`, including scheduled notes) and drops alert clips. A conversation reply may still play. The saved mute is separate. A stricter alert, such as drowsy stop versus engine stop, breaks quiet once. The same alert repeating does not.
- Talk states are idle, listening, transcribing, thinking, speaking, followup, and error. The Ask button is the demo path. A typed question is the fallback. End, hide, and unmount do not upload. Optional `conversationId`, `turnId`, and `generation` let a late reply be dropped before it is stored or spoken. Old clients omit them.
- Energy VAD ends a phrase; silence is not sent. Follow-up listening is 10 seconds and does not need "hey neuron". Browser wake remains a best-effort extra and is not claimed to be local.
- Pause demo exists only for `?presenter=1` on simulated data. It stops the simulator clock. It does not freeze OBD. Streaming STT/TTS was not verified for Blaze and is not implemented. The path is one whole utterance, one guarded reply, then file TTS.

### Conversation lifecycle fixes (2026-10-16, later the same day)

Astra had already started the identity, VAD and multipart work. The remaining holes that were closed:

- A reply can be spoken after the HTTP response marks the turn done. Cancel or a newer turn still stops that audio before it is published. `spoken` means queued.
- Conversation ids are random and scoped to the vehicle session on the server. A cancel for one session does not cancel another.
- VAD no longer trains its noise floor on the speech it is trying to confirm. At an 80 ms tick, a moderate tone counts as speech. The 10 s follow-up timer waits for speech to **start**; the 20 s limit starts at onset.
- While the microphone is open, End is visible next to the indicator, not only inside the panel. Hey Neuron is opt-in and is switched off by End.

### Voice latency, cache and transcript dividers — 2026-10-17

`backend/voice.py` now separates alert and talk job pools (two workers each), with separate three-worker part pools and a global four-request provider cap. Parts publish in index order; cancel and failed earlier parts prevent later publication. Only creation POSTs retry once on 429/502/503/504 or a connect failure (not a read timeout: the job may exist), never an accepted job's download. Playback priorities still belong solely to `audio-focus.ts`.

Exact spoken text plus selected voice/model/language/speed/format keys a persistent atomic cache in `backend/var/voice-cache` (beside the voice folder because `./demo.sh` wipes `var/voice`; `BLAZE_VOICE_CACHE_DIR` overrides) (200 entries / 100 MB by default). Registered clips, pending publications and active downloads pin their files. Pinned entries can prevent admission; valid new audio still plays uncached. `BLAZE_VOICE_CACHE=0` disables it; `BLAZE_VOICE_CACHE_MAX_FILES` and `BLAZE_VOICE_CACHE_MAX_MB` set budgets. Tests and browser harnesses use fakes, never paid providers. Manual opt-in scripts and log interpretation: `../docs/demo-runbook.md` §9.

`TalkMetrics.replyToAudioMs` measures reply text → first audio-start event, null for text-only/cancelled turns (zero when audio preceded text). Metrics log only with `?debug=1`; this is a playback event, not a microphone measurement of the speaker. Scene/language changes now retain a bounded UI transcript with archived rows and `li[role=separator]`, superseding the earlier clear-panel description; vehicle changes still clear it. Old turns cannot be retried and conversation IDs still isolate model context. Preserve footer notices and testids. Run the alert-control, conversation-lifecycle and present harnesses on isolated ports/output directories.
